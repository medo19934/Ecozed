# Latif Kids — feature status against the full product specification

Checked on 2026-11-17 against the "senior product designer … childcare platform" specification, the owner PDF (`docs/latif-kids-hub-reference.pdf`), and the code on branch `claude/latif-kids-saas-setup-lbtxt1` (commit 82a414d).

Status values used below:

- **Done** — implemented and checked by automated tests and/or a browser run.
- **Partial** — part of the requirement exists. What is missing is listed.
- **Blocked** — needs credentials, a provider or an owner decision.
- **Missing** — not implemented.

> **Deployment:** Netlify refuses new deploys ("Account credit usage exceeded"). The live sites run an older build. Everything after commit `29a5d0a` exists only in the repository and in the APK build.

Staff press "Mark paid".                                                                                                                 | —                                                                                                                             |

## 3. Externally blocked

- **Netlify deploys:** account credits exhausted. Credits must be added (or wait for the monthly reset) before anything new goes live.
- **SMS / email** (password recovery, reminders), **push notifications** (Expo/FCM/APNs keys), **payment provider**, **Google Maps key**, **AI provider**, **iOS build** (Apple developer account).

## 4. Known defects / unverified

- The new role dashboards (commit 82a414d) are not verified in a browser. The verification script failed on its own selector before checking the pages.
- `PUBLIC_DEMO=true` is insecure by design.
- The live API still runs a build without the subscriptions, daily-reports and reports endpoints. The current APK's Reports tab will error until the API is redeployed.

## 5. Suggested order to close the gaps

1. Owner decision on sign-in (demo cards vs. passwords) before any real family data is entered.
2. Redeploy once Netlify credits are available, then run the all-roles browser sweep against the live site.
3. Notifications (in-app first, then push), pickup authorization, admission statuses/history, and privacy/terms pages.
4. A committed Playwright suite plus a CI workflow (lint, typecheck, unit, e2e).
5. Remaining docs: permission matrix, data model, backup/rollback.
